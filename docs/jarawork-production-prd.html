Executive Summary

JaraWork is an autonomous marketplace-order-to-worker platform built on Arc. Orders from Jaramarket, Amazon, eBay, and Jumia are ingested by a Circle developer-controlled agent wallet, posted as USDC escrow orders on-chain, claimed by workers worldwide, and paid automatically on delivery confirmation — no human intervention required.

The platform is functionally complete for testnet demonstration. This document catalogues every gap that must be closed before a public mainnet launch, prioritised by impact and estimated engineering effort.

What Is Already Complete

Smart contract (escrow, roles, fees, disputes)
Autonomous agent (poll, create, release, refund)
Frontend — all 5 tabs wired
Wallet connection + chain switching
USDC approve → createOrder two-step flow
Worker claim + delivery submission
Auto-release payment (24h timer)
Auto-refund unclaimed orders (7-day timer)
Jaramarket adapter (REST + Bearer token)
Jumia adapter (direct + relay fallback)
Amazon adapter (stub — relay not implemented)
eBay adapter (stub — OAuth not implemented)
Platform role set on contract
Agent wallet created + funded (9 USDC)

Section 1 — Critical Gaps Blocks Real Use

These items must be resolved before any real user can safely interact with the platform.

1.1  Order Dedup Persistence P0 Small

Risk
Every agent restart wipes the in-memory postedKeys Set. On the next poll, all previously posted marketplace orders are re-submitted as duplicates — double-charging the agent wallet and flooding the order board with ghost orders.

Required Fix

Persist postedKeys to .data/posted-keys.json. Read on startup; append atomically on each new post. Mount a Render persistent disk to .data/ so the file survives redeployments.

Acceptance Criteria

  • Restarting the agent does not re-post any previously posted order.
  • .data/posted-keys.json is excluded from version control but present at runtime.

1.2  Amazon SP-API Relay P0 Medium

Current State
GET /api/amazon/orders returns [] with a stub note. No Amazon orders will ever flow until this is implemented.

Required Fix

  1. Accept AMAZON_CLIENT_ID, AMAZON_CLIENT_SECRET, AMAZON_REFRESH_TOKEN, AMAZON_MARKETPLACE_ID from .env.
  2. Exchange refresh token for a bearer token via POST https://api.amazon.com/auth/o2/token.
  3. Sign GET /orders/v0/orders?OrderStatuses=Unshipped with AWS SigV4.
  4. Map each order to { externalId, title, description, usdcAmount, sourceMarketplace: 'amazon' }.

Credentials Required

AMAZON_CLIENT_ID · AMAZON_CLIENT_SECRET · AMAZON_REFRESH_TOKEN · AMAZON_MARKETPLACE_ID

Acceptance Criteria

  • With valid credentials, agent polls Amazon and posts orders on-chain automatically.
  • Missing credentials returns empty array gracefully — no crash.

1.3  eBay Fulfillment API Relay P0 Medium

Current State
GET /api/ebay/orders returns [] with a stub note. No eBay orders flow until this is implemented.

Required Fix

  1. Accept EBAY_CLIENT_ID and EBAY_CLIENT_SECRET from .env.
  2. Fetch OAuth2 client credentials token from https://api.ebay.com/identity/v1/oauth2/token.
  3. Call GET /sell/fulfillment/v1/order?filter=orderfulfillmentstatus:{NOT_STARTED}.
  4. Cache the token for its expires_in duration.
  5. Map to MarketplaceOrder format.

Credentials Required

EBAY_CLIENT_ID · EBAY_CLIENT_SECRET

Acceptance Criteria

  • eBay orders appear on the board and are posted on-chain after agent poll.
  • Token is cached — not re-fetched on every cycle.

1.4  Low-Balance Alert on Agent Wallet P0 Small

Risk
When the agent wallet USDC balance drops to zero, all order creation fails silently. Workers see no orders. The platform appears broken with no visible cause.

Required Fix

  • Add LOW_BALANCE_THRESHOLD_USDC env var (default: 5.00).
  • Check balance at the start of every poll cycle. Log an error action and show a red banner in the Agent tab when below threshold.
  • Optionally: POST to ALERT_WEBHOOK_URL with low-balance JSON payload.

Acceptance Criteria

  • Agent tab shows a prominent "Low Balance" warning when balance < threshold.
  • Warning clears automatically once balance is topped up.

1.5  Dispute Resolution UI P0 Small

Risk
Disputed orders lock USDC in escrow forever. The resolveDispute function exists on the contract but has no UI. Any dispute is permanently stuck.

Required Fix

Add an Admin section to the Agent tab, visible only when the connected wallet is the contract owner:

  • List all disputed orders with title, buyer, worker, and USDC amount.
  • Two action buttons per order: Pay Worker and Refund Buyer.
  • Both call resolveDispute(key, favorWorker) via the wagmi write hook pattern.

Acceptance Criteria

  • Owner wallet can resolve any dispute in one click.
  • Non-owner wallets do not see the admin section.
  • Resolved orders leave the disputed list after tx confirmation.

Section 2 — Important Gaps Reliability

These items do not block launch but will cause friction or data loss in production under real load.

2.1  Jaramarket Webhook (vs. 60s Polling) P1 Medium

Impact
New Jaramarket orders can take up to 60 seconds to appear on JaraWork. Workers may claim orders from competing platforms first.

Required Fix

Add POST /api/jaramarket/webhook to the agent server. Validate the payload with an HMAC check using JARAMARKET_WEBHOOK_SECRET. Process the order immediately on receipt — no waiting for the next cycle.

Acceptance Criteria

  • New Jaramarket orders appear on-chain within 5 seconds of being placed.
  • Invalid/unsigned payloads are rejected with HTTP 401.

2.2  Order Board Pagination P1 Small

Impact
getOpenOrders() returns all keys in a single RPC call. At 500+ orders this becomes slow and may time out.

Required Fix

Replace getOpenOrders() with paginated reads via getOrderKeys(offset, limit). Show 20 orders per page with a "Load more" control. Total count from getOrderCount().

Acceptance Criteria

  • Order Board loads in under 1 second with 500+ total orders.
  • "Load more" appends the next page without a full re-fetch.

2.3  Worker Notifications P1 Medium

Impact
Workers have no way to know when a new order arrives. Serious workers cannot monitor the app constantly.

Options

  • Option A — Web Push: Prompt for notification permission. Push to subscribed workers when a new order is posted.
  • Option B — Webhook/email: WORKER_ALERT_WEBHOOK_URL in .env. POST order details; connect to SendGrid, Resend, or Slack.

Acceptance Criteria

  • Workers receive notification within 90 seconds of a new order being posted on-chain.

2.4  Agent Error Recovery / Retry Queue P1 Medium

Risk
If approveUsdc succeeds but createOrder fails, the approval is consumed and the order is silently dropped. No retry occurs.

Required Fix

Introduce a retry queue persisted to .data/retry-queue.json. On createOrder failure after a successful approve: add to queue with retryAt = now + 60s. Retry up to 3 times. After 3 failures: log an error action and drop the entry.

Acceptance Criteria

  • Failed createOrder after successful approve is retried up to 3 times.
  • After 3 failures, Agent tab shows an error with the order ID and reason.

Section 3 — Nice to Have Polish

3.1  Order Search and Filtering P2 Small

Add a filter bar to the Order Board: filter by marketplace (All / Jaramarket / Amazon / eBay / Jumia), USDC amount range (min/max), and sort order (newest / highest value). All filtering is client-side against the already-fetched order list — no contract changes needed.

3.2  Worker Reputation / Completion Score P2 Large

Workers are currently anonymous addresses. Add a simple on-chain or off-chain reputation system: count completed orders per worker address from contract events. Display a completion-rate badge on order cards. Optionally allow buyers to restrict claiming to workers above a minimum score.

3.3  Admin Panel Tab P2 Small

Replace the "Activate Platform Role" card in the Agent tab with a dedicated owner-only Admin section: current fee bps (editable), platform address (changeable), claim timeout setting, and the dispute resolution queue. Consolidates all owner actions in one place.

3.4  Delivery Proof Standards P2 Small

The deliveryProof field currently accepts any free-form string. Define a structured format: physical goods require CARRIER:TRACKINGNUMBER; digital work requires a URL or IPFS hash. Validate client-side before submission. Display detected type (tracking link, IPFS viewer, URL preview) in the order card.

3.5  Mainnet Migration Checklist P2

  • Obtain an independent security audit of JaraWorkEscrow.sol
  • Replace testnet Circle API key (TEST:...) with a LIVE:... key
  • Re-register entity secret against the live key
  • Fund agent wallet with real USDC on Arc mainnet
  • Deploy contract with mainnet USDC address (0x3600000000000000000000000000000000000000)
  • Update all arcTestnet chain references to arc (chain ID 4506)
  • Remove "Arc Testnet" badges from UI
  • Set up uptime monitoring on the Render service
  • Configure ALERT_WEBHOOK_URL for low-balance and error alerts
  • Test full end-to-end flow on mainnet with minimum amounts before opening to public
